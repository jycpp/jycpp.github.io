大模型部署4个案例说清楚

4 个案例讲清楚自研大模型的部署过程

很多人训完模型会卡在一个问题：

“我的 model.safetensors 训出来了，怎么让别人用上？”

答案不是“部署”两个字，而是先回答几个问题： - 跑在服务器还是本机还是手机？ - 是 LLM 还是 ASR / 视觉小模型？ - 用 Python 服务，还是 C++ / Kotlin / Swift 直接跑？ - 用 HuggingFace 格式、GGUF、ONNX 还是 NCNN？

下面用 4 个案例把“训练格式 → 部署格式 → 推理引擎 → 服务/端侧调用”讲清楚。

4个案例覆盖了训练模型的常用场景

主要的注意事项

  1. 训练格式不管是 safetensors 还是 pytorch_model.bin，都不要直接部署。
  2. HuggingFace 格式给服务器，GGUF 给本地/端侧 LLM，ONNX 是中间格式，NCNN 是端侧 C++ 落地格式。
  3. FastAPI / Kotlin / Swift 都不“懂模型”，它们调用推理引擎；推理引擎才读模型文件。

案例 1：服务器部署自研 7B LLM（vLLM）

1. 训练产物是什么

这就是标准 HuggingFace 格式： - config.json：模型结构 - tokenizer*：分词器 - model.safetensors：权重

说明：vLLM 不需要 ONNX，也不需要 GGUF。它直接读 HuggingFace 格式，因为 vLLM 本身就是服务器级 LLM 推理引擎，内部自己做算子优化、PagedAttention、批处理。

2. 为什么不直接用 model.generate() 上线

transformers 的 model.generate() 能跑，但： - 不支持高并发 - 没有高效 KV Cache 管理 - 没有 OpenAI 兼容接口 - 工程化能力弱

所以生产里通常用 vLLM / TGI 这种“推理服务引擎”。

3. 启动 vLLM 服务

参数含义： - --model：HuggingFace 模型目录，不是单个文件 - --host 0.0.0.0：允许其他机器访问；localhost 只能本机 - --port 8000：HTTP 服务端口 - --dtype auto：自动选 fp16/bf16 - --max-model-len 4096：最大上下文，防止显存爆掉

FastAPI 不加载模型，而是： - 做鉴权 - 拼系统提示 - 多模型路由 - 限流 - 转发给 vLLM

案例 2：本地 / 开发机用 Ollama 跑量化 LLM

1. 为什么要转 GGUF

HuggingFace 格式适合训练和服务端加载，但不适合： - 笔记本 - 单 CPU / 小显存 - 快速本地试跑

所以需要两步： 1. 转 GGUF：从训练生态进入 llama.cpp 推理生态 2. 量化：把 16-bit 权重压成 4-bit，省显存/内存

2. 第一步：HF → FP16 GGUF

参数说明： - ./my-7b：HuggingFace 模型目录 - --outfile：输出的 GGUF 文件 - --outtype f16：权重保持 16 位浮点，不做量化
👉 这一步只是“换容器”，不是压缩

3. 第二步：FP16 GGUF → Q4_K_M GGUF

参数说明： - 输入：FP16 GGUF - 输出：量化后 GGUF - Q4_K_M：4-bit 左右、质量/体积平衡最好的量化档位之一
- 7B 模型：FP16 约 14GB，Q4_K_M 约 4–5GB

重要：永远从 FP16 GGUF 再量化，不要从 Q4 再量化成 Q2，否则误差会叠加。

4. Modelfile 是干什么的

Modelfile 不是模型文件，也不是镜像，而是“模型 + 行为配置”的说明书，类似 Dockerfile。

逐行说明：

  • FROM：底座模型，这里直接指向本地 GGUF
  • SYSTEM：每次对话都带上的“人设 / 规则”
  • TEMPLATE：把 system / user / assistant 拼成模型训练时见过的格式
    👉 模板错了，模型就会“不听指令”
  • temperature：创造性
  • top_p：采样范围
  • num_ctx：上下文窗口大小
  • repeat_penalty：防复读

案例 4：端侧 ASR（Conformer → ONNX → NCNN）

1. Conformer 模型和前面 3 个一样吗

不一样在任务域：

案例 模型 任务
1 Decoder LLM 文本生成
2 Decoder LLM 本地对话
3 小 LLM 端侧对话
4 Conformer / Zipformer 语音识别

Conformer 也是 PyTorch 训出来的，但： - 输入是 log-Mel 声学特征 - 输出是 token / CTC / RNNT - 不是聊天模型

2. PyTorch → ONNX

目的： > 把“PyTorch 动态图”变成“静态计算图”，方便跨框架和端侧引擎加载。

3. ONNX → NCNN

产物： - .param：网络结构 - .bin：权重

4. C++ 直接跑

这里没有 Python、没有 Docker、没有 HTTP，就是 C++ 读文件、跑矩阵运算。
